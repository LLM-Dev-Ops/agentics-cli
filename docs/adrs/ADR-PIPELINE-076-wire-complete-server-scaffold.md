# ADR-PIPELINE-076: Wire-Complete Server Scaffold — /metrics and /health/ready Present by Default

**Status:** Accepted
**Date:** 2026-04-12
**Priority:** HIGH — Observability gap flagged on every readiness review
**Originating Review:** Ramco Aviation Catering Readiness Review (2026-04-12), Observability 6/10
**Prior Reviews:** OPERA Sustainability Review (2026-04-11) noted the same class of defect
**Builds on:** ADR-PIPELINE-051 (Observability Foundation), ADR-PIPELINE-069 (Scaffold Ownership), ADR-PIPELINE-064 (Typed Hono Context)

## Context

Two consecutive readiness reviews have flagged the same observability gap:

> "Missing for pilot: (1) /metrics endpoint (Prom-format counters for ERP success/failure, circuit state, recommendation throughput) — the scaffold's middleware.ts hinted at this but it wasn't wired in; (2) /health/ready vs /health/live split; (3) OpenTelemetry trace propagation..."
> — Ramco review 2026-04-12, Observability 6/10
>
> "Wire the existing metricsHandler into api/server.ts and add histograms on opera.post.duration_ms..."
> — OPERA review 2026-04-11, Observability 7/10

The scaffold already emits `metricsHandler` inside `middleware.ts`. The coding agent consistently **does not wire it into the generated server**. Investigation shows the prompts say "Wire `metricsHandler` from middleware.ts to GET /metrics" — but the agent builds the server from scratch and forgets the wiring in roughly 1 run out of 2.

The failure mode is systematic: the coding agent treats server construction as a blank-slate task. It writes `const app = express()` or `const app = new Hono()` and starts adding domain routes without ever importing the scaffold middleware, because there is no scaffolded `base-app.ts` to extend.

**The fix is to ship a complete, wire-correct server base module that the generator extends rather than replaces.** The coding agent's job becomes "add your domain routes to `createBaseApp()`" instead of "build an Express/Hono app from scratch." The base includes correlation middleware, request logging, metrics handler, liveness, readiness, error handler, and CORS — all wired in the right order.

A PGV rule enforces that the three required routes (`/metrics`, `/health/live`, `/health/ready`) exist in the final project.

## Decision

### 1. Scaffold a Complete `src/api/base-app.ts`

Add a new scaffold constant `BASE_APP_SCAFFOLD` in `src/pipeline/auto-chain.ts`. Emitted to `src/api/base-app.ts` in every generated project.

```typescript
// Auto-generated by Agentics pipeline (ADR-PIPELINE-076)
// Complete Hono app base with middleware, metrics, liveness, readiness,
// and an extension point for domain routes. DO NOT rewrite — extend via
// `createBaseApp(container).route(...)` or `.use(...)` from your own
// routes module.
import { Hono } from 'hono';
import { randomUUID } from 'node:crypto';
import { runWithCorrelation, createLogger } from '../logger.js';
import { recordHistogram, incrementCounter, metricsHandler } from '../middleware.js';

export interface HealthCheck {
  readonly name: string;
  readonly check: () => Promise<{ ok: boolean; detail?: string }>;
}

export interface BaseAppDeps {
  readonly serviceName: string;
  readonly version: string;
  readonly readiness: readonly HealthCheck[];
}

export interface BaseAppContextVariables {
  correlationId: string;
  startedAt: number;
}

const logger = createLogger('base-app');

/**
 * Build the wire-complete base app. The returned instance already has:
 *   - correlationId middleware (AsyncLocalStorage-scoped, ADR-074)
 *   - request logging with duration histogram
 *   - GET /health/live   (process is up)
 *   - GET /health/ready  (every readiness check passes)
 *   - GET /metrics       (Prometheus text format, ADR-051)
 *   - Zod validation error handler
 *
 * Add domain routes with `.route('/api/...', yourRouter)`.
 */
export function createBaseApp(deps: BaseAppDeps): Hono<{ Variables: BaseAppContextVariables }> {
  const app = new Hono<{ Variables: BaseAppContextVariables }>();

  // Correlation ID — must be first so every downstream log carries it
  app.use('*', async (c, next) => {
    const id = c.req.header('x-correlation-id') ?? randomUUID();
    c.set('correlationId', id);
    c.set('startedAt', Date.now());
    c.header('X-Correlation-Id', id);
    await runWithCorrelation(id, async () => {
      await next();
    });
  });

  // Request logging
  app.use('*', async (c, next) => {
    await next();
    const durationMs = Date.now() - c.get('startedAt');
    const status = c.res.status;
    logger.info('http.request', {
      method: c.req.method,
      path: c.req.path,
      status,
      durationMs,
    });
    incrementCounter('http_requests_total', {
      method: c.req.method,
      status: String(status),
    });
    recordHistogram('http_request_duration_ms', durationMs, {
      method: c.req.method,
    });
  });

  // Liveness — always returns OK if the process is running
  app.get('/health/live', (c) => {
    return c.json({
      status: 'ok',
      service: deps.serviceName,
      version: deps.version,
      uptime_sec: Math.round(process.uptime()),
    });
  });

  // Readiness — runs every registered check
  app.get('/health/ready', async (c) => {
    const results: Array<{ name: string; ok: boolean; detail?: string }> = [];
    for (const check of deps.readiness) {
      try {
        const r = await check.check();
        results.push({ name: check.name, ...r });
      } catch (err) {
        results.push({
          name: check.name,
          ok: false,
          detail: err instanceof Error ? err.message : String(err),
        });
      }
    }
    const allOk = results.every(r => r.ok);
    return c.json(
      { status: allOk ? 'ready' : 'not-ready', checks: results },
      allOk ? 200 : 503,
    );
  });

  // Metrics — Prometheus text format
  app.get('/metrics', (c) => {
    const text = metricsHandler();
    return c.text(text, 200, { 'Content-Type': 'text/plain; version=0.0.4' });
  });

  // Error handler — last, so it catches everything above
  app.onError((err, c) => {
    logger.error('http.error', err as Error, {
      method: c.req.method,
      path: c.req.path,
    });
    const status = (err as { httpStatus?: number }).httpStatus ?? 500;
    return c.json(
      {
        error: {
          message: err.message,
          code: (err as { code?: string }).code ?? 'INTERNAL_ERROR',
        },
      },
      status as 500,
    );
  });

  return app;
}
```

### 2. Hono and Express Variants

Ship TWO `base-app` scaffolds — one for Hono (shown above, used by the majority of recent prototypes) and one for Express (used by some legacy targets). The generator picks which one to use based on the framework detected in Phase 4.

`BASE_APP_SCAFFOLD_HONO` and `BASE_APP_SCAFFOLD_EXPRESS` constants in `auto-chain.ts`.

### 3. Update `MIDDLEWARE_SCAFFOLD` to Export a Pure `metricsHandler()`

Current scaffold `metricsHandler` is an Express-style `(req, res) => void`. The Hono base app needs a string-returning variant. Refactor the middleware scaffold to export both:

- `metricsHandler()` — returns the Prometheus text (pure)
- `metricsHandlerExpress(req, res)` — Express-compatible wrapper
- `metricsHandlerHono(c)` — Hono-compatible wrapper

The base apps call the framework-specific wrapper; service code that wants the raw text (for a scraped endpoint in a different framework) calls the pure version.

### 4. PGV-018 — /metrics and /health Routes Must Exist

Add to the post-generation validator (ADR-065):

| ID | Rule | File Pattern | Check |
|---|---|---|---|
| PGV-018 | Generated project must expose `/metrics`, `/health/live`, `/health/ready` | `src/api/**/*.ts`, `src/server/**/*.ts`, `src/app.ts` | All three route strings appear in at least one matched file |

Error severity. If the base app is imported, all three are automatically present; the rule is a safety net for hand-edited projects.

### 5. Implementation Prompt Rewrite

Replace the current "Wire metricsHandler to GET /metrics" instructions with the new extension pattern:

> ## HTTP Server (ADR-PIPELINE-076)
>
> DO NOT build the app from scratch. The scaffold provides `src/api/base-app.ts`
> with correlation middleware, request logging, `/metrics`, `/health/live`,
> `/health/ready`, and the error handler all wired in the correct order.
>
> Your job is to:
>
> 1. Create `src/api/routes/<domain>.ts` exporting a Hono router with your domain routes
> 2. In `src/server.ts`, import `createBaseApp` from `./api/base-app.js`
> 3. Call `createBaseApp({ serviceName, version, readiness: [...] })`
> 4. Mount your domain routers with `.route('/api/<domain>', yourRouter)`
> 5. Add readiness checks for every external dependency (database, ERP, queues)
>
> Example:
>
> ```typescript
> import { createBaseApp } from './api/base-app.js';
> import { cateringRouter } from './api/routes/catering.js';
> import { serve } from '@hono/node-server';
>
> const app = createBaseApp({
>   serviceName: 'cater-waste-copilot',
>   version: '0.1.0',
>   readiness: [
>     { name: 'sqlite', check: async () => ({ ok: db.open }) },
>     { name: 'ramco', check: async () => ({ ok: !erpAdapter.breaker.isOpen() }) },
>   ],
> });
>
> app.route('/api/catering', cateringRouter);
>
> serve({ fetch: app.fetch, port: config.port });
> ```
>
> DO NOT re-implement correlation middleware, request logging, /metrics,
> or health checks — they are already wired and PGV-018 will fail the
> build if any of /metrics, /health/live, /health/ready are missing.

### 6. OWNED_SCAFFOLD_MODULES Entry

Add:

```typescript
{ path: 'src/api/base-app.ts',
  exports: ['createBaseApp', 'BaseAppDeps', 'BaseAppContextVariables', 'HealthCheck'] },
```

PGV-012 blocks any generator file from redeclaring `createBaseApp`.

### 7. Default Readiness Checks

The scaffold prompt includes a sensible default readiness-check list (for domains that don't specify their own):

```typescript
readiness: [
  { name: 'process', check: async () => ({ ok: true }) },
  // Add one entry per external dependency. The default above passes
  // unconditionally — replace it before the pilot goes live.
]
```

With a stern comment warning that an unconditional-pass readiness check is a security and operational anti-pattern. A separate PGV rule (PGV-019) flags files where `readiness:` is empty OR contains only unconditional passes when more than one service dep exists.

## Implementation

1. Extract two new scaffold constants `BASE_APP_SCAFFOLD_HONO` and `BASE_APP_SCAFFOLD_EXPRESS` in `src/pipeline/auto-chain.ts`.
2. `copyPlanningArtifacts()` writes `src/api/base-app.ts` from the Hono scaffold by default; emit Express variant when the generator detects Express in Phase 4.
3. Refactor `MIDDLEWARE_SCAFFOLD` to export `metricsHandler()` as the pure variant plus framework-specific wrappers.
4. Add `RULE_PGV_018` and `RULE_PGV_019` to `post-generation-validator.ts`.
5. Add `src/api/base-app.ts` entry to `OWNED_SCAFFOLD_MODULES`.
6. Rewrite the `## HTTP Server` section of `CROSS_CUTTING_FOOTER_BODY` in `prompt-generator.ts`.
7. Tests:
   - `tests/unit/pipeline/scaffold/base-app-076.test.ts` — compiles the scaffold via `ts.transpileModule`, boots a test Hono app, verifies all three routes respond
   - PGV-018 positive + negative cases
   - PGV-019 positive + negative cases

## Acceptance Criteria

1. Every generated project contains `src/api/base-app.ts`.
2. Every generated project exposes `/metrics`, `/health/live`, and `/health/ready` on first run — verified by PGV-018.
3. Liveness returns 200 when the process is up.
4. Readiness returns 503 when any registered check fails.
5. `/metrics` returns Prometheus text format with at least `http_requests_total` and `http_request_duration_ms` series populated by the base app's built-in middleware.
6. Correlation ID in every log line matches the request's `X-Correlation-Id` header (integration with ADR-074).
7. PGV-019 fires against a synthetic fixture where `createBaseApp` is called with an empty readiness list alongside a `db` dependency.
8. The implementation prompt contains the `createBaseApp` snippet verbatim.

## Consequences

### Positive

- Every generated project is observability-ready on day zero. Pilot teams can point Grafana at `/metrics` and Kubernetes liveness/readiness probes at the health endpoints without any integration work.
- The coding agent stops making the recurring `metricsHandler-unwired` mistake because it no longer writes its own server from scratch.
- Shared middleware ordering (correlation → logging → routes → error handler) is enforced by a single template, so every project gets it right.
- PGV-019's unconditional-pass readiness check is a cheap catch for a common configuration oversight.

### Negative

- The base app is opinionated — services that need a non-Hono / non-Express framework have to build their own. Acceptable for ~95% of pilot targets; rare exceptions document the override pattern.
- Changing default middleware order requires updating the scaffold, not individual projects. This is the right trade-off (consistency) but means ad-hoc experimentation happens downstream.
- `metricsHandler()` becomes stateful — the pure variant reads module-scope counter/histogram maps. Acceptable, documented, and matches Prometheus client library conventions.
