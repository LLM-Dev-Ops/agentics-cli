# ADR-042: SPARC and DDD Must Produce Domain-Specific Models, Not CRUD Wrappers

**Status**: Proposed
**Date**: 2026-03-26
**Severity**: P0 — SPARC and DDD feed all downstream phases

## Context

The pipeline audit on a carbon strategy simulation platform revealed that the SPARC specification and DDD model are generic CRUD wrappers that could describe any system:

### SPARC Failures
- Functional requirements RD-001 through RD-006: "The system must model and manage {EntityName} as a core domain concept" — identical template for each service
- RD-007: The entire user prompt pasted verbatim as a single requirement — not decomposed
- No requirements for: simulation methodology, confidence intervals, strategy scoring, market data sources, regulatory scenario parameters, or NetSuite record mappings
- Rust is mentioned only once in passing despite the user explicitly requesting it for financial modeling

### DDD Failures
- 12 bounded contexts, all with identical structure: Create{X}, Update{X}, Query{X}
- Context descriptions: "Manage {Entity} domain logic, CRUD operations, business rules, and event handling"
- No domain-specific commands: SimulateCarbonStrategy, ProjectMarketPrices, CompareStrategies, CalculateComplianceGap
- No domain-specific aggregates: EmissionsBaseline (with facility, scope, year), SimulationRun (with parameters, results, confidence), StrategyScenario (with NPV, risk score, compliance gap)
- 6 of 12 contexts are infrastructure adapters (netsuite-integration, oracle-integration, bigquery-integration, etc.) — these are not domain bounded contexts
- Ubiquitous language definitions are just the context descriptions repeated

### Root Cause
The SPARC specification is generated by the `sparc-specification.ts` template which extracts service names from the simulation output and wraps each in a generic requirement template. The DDD model is generated by `ddd-generator.ts` which creates one bounded context per SPARC service with generic Create/Update/Query commands. Neither phase uses the LLM to understand the user's actual domain.

## Decision

### A. SPARC Functional Requirements Must Be Domain-Decomposed
The SPARC specification generator must:
1. Pass the full user prompt to the LLM with explicit instructions to decompose it into 10-20 domain-specific functional requirements
2. Each requirement must describe a specific capability, not "model and manage {Entity}"
3. Requirements must reference the user's technology choices (Rust for simulation, TypeScript for orchestration, etc.)
4. The user prompt must NOT appear as a single monolithic requirement

Example for carbon strategy:
- "FR-001: The system must model facility-level emissions baselines with Scope 1/2/3 breakdown, supporting annual and quarterly aggregation by business unit and region"
- "FR-002: The system must simulate carbon credit price trajectories using geometric Brownian motion with configurable drift and volatility parameters"
- "FR-003: The system must compare N strategy scenarios across 4 dimensions: total cost, emissions reduction, compliance risk score, and strategic alignment score"

### B. DDD Bounded Contexts Must Reflect the Domain, Not Infrastructure
The DDD generator must:
1. NOT create bounded contexts for infrastructure adapters (netsuite-integration, bigquery-integration, etc.) — these are adapters inside the `integrations/` or `erp/` folder, not domain contexts
2. Create bounded contexts that reflect the user's actual domain problem
3. Each context must have domain-specific commands and queries — not generic CRUD
4. Aggregate roots must have typed fields specific to the domain

Example for carbon strategy:
- **EmissionsBaseline** context: commands: RecordFacilityEmissions, AggregateByBusinessUnit, SetReductionTarget; queries: GetBaselineByFacility, GetBaselineByScope, GetReductionProgress
- **MarketSimulation** context: commands: RunPriceSimulation, ConfigureMarketScenario, SetVolatilityParameters; queries: GetProjectedPrices, GetConfidenceIntervals
- **StrategyEngine** context: commands: CompareStrategies, ScoreScenario, ApproveForExecution; queries: GetStrategyRanking, GetTradeoffMatrix

### C. LLM Must Generate Both SPARC Requirements and DDD Contexts
The deterministic template approach has proven inadequate. Both SPARC requirement decomposition and DDD context generation must use LLM calls with the full user prompt, with explicit instructions to produce domain-specific output.

### D. Integration Adapters Are NOT Bounded Contexts
Remove infrastructure integration contexts (netsuite-integration, oracle-integration, bigquery-integration, etc.) from the DDD model. These belong in `erp/` and `integrations/` folders as adapter code, referenced by ADRs — not as domain bounded contexts.

## Consequences

### Positive
- SPARC requirements drive domain-specific implementation
- DDD model reflects actual business domain
- Generated code implements real business logic instead of CRUD stubs
- Implementation prompts inherit domain specificity

### Negative
- Additional LLM calls in Phase 2 (requirement decomposition + DDD generation)
- Longer Phase 2 execution time (~30-60s per LLM call)
- Requires more sophisticated prompt engineering

## Implementation

1. `sparc-specification.ts` — Add LLM call to decompose user prompt into 10-20 domain-specific functional requirements
2. `ddd-generator.ts` — Filter out infrastructure adapter contexts; use LLM to generate domain-specific commands, queries, and aggregate fields
3. `ddd-generator.ts` — DDD enrichment prompt must include full user requirements and demand domain-specific invariants
4. Both generators — Include the user's technology stack choices in the LLM prompt context
