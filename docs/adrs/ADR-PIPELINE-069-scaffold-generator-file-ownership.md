# ADR-PIPELINE-069: Scaffold vs. Generator File Ownership — No Duplicate Cross-Cutting Modules

**Status:** Accepted
**Date:** 2026-04-11
**Priority:** MEDIUM — Dead code + drift risk in every generated project
**Originating Review:** OPERA Sustainability Prototype Readiness Review (2026-04-11), Code Quality 8/10

## Context

The OPERA review noted:

> "Two files re-declare `CircuitBreaker` (scaffold + `src/erp/circuit-breaker.ts`); only one is used, but remove the dead copy."

The defect is structural: `src/pipeline/auto-chain.ts` emits `middleware.ts` into the scaffold directory containing a full `CircuitBreaker` class (see lines ~382–425). The coding agent, reading the implementation prompt independently, then generates `src/erp/circuit-breaker.ts` with its own implementation. Both files land in the same project. Only one is imported. The other is dead code plus a future drift hazard: if the scaffold fixes a bug in `CircuitBreaker`, the generator's copy does not benefit.

The same pattern will hit `Logger`, `AppConfig`, `ValidationError`, correlation-id middleware, and every other cross-cutting module the scaffold emits once generators grow more ambitious. We need an explicit ownership rule before the surface area expands further.

## Decision

### 1. Define the Ownership Split

Every module in the generated project is owned by exactly one emitter:

| Layer | Owner | Examples | Rationale |
|---|---|---|---|
| **Cross-cutting infrastructure** | Scaffold (`auto-chain.ts`) | `logger.ts`, `config.ts`, `errors.ts`, `middleware.ts`, `simulation-lineage.ts`, `circuit-breaker.ts`, `audit-log.ts` | Same shape in every project; pipeline must guarantee correctness |
| **Domain types & seed data** | Generator (phase 3+) | `domain/types.ts`, `domain/seed.ts` | Query-specific; scaffold has no context |
| **Domain services** | Generator | `services/**/*.ts` | Business logic |
| **External adapters** | Generator | `erp/opera-adapter.ts`, `db/postgres-client.ts` | System-specific |
| **HTTP layer** | Scaffold base + generator routes | Scaffold emits `api/app.ts` with middleware wiring; generator adds `api/routes/*.ts` | Shared middleware, per-query routes |
| **Demo script** | Hybrid: scaffold emits a *template* with slots; generator fills slots | `demo.ts` | Bridges the two |

The rule is: **if the module exists in the scaffold, the generator MUST NOT emit a module with the same class/function exports.** The generator imports from the scaffolded file.

### 2. Move `CircuitBreaker` to a Dedicated Scaffold File

Today `CircuitBreaker` is buried inside `middleware.ts`. Extract it into its own scaffold file `src/circuit-breaker.ts` so adapters can import it without pulling all middleware:

```typescript
// .agentics/plans/scaffold/src/circuit-breaker.ts
// Auto-generated by Agentics pipeline (ADR-PIPELINE-069)
import { createLogger } from './logger.js';

export class CircuitBreaker { /* ... */ }
```

`middleware.ts` re-exports it for backward compatibility:

```typescript
export { CircuitBreaker } from './circuit-breaker.js';
```

### 3. Scaffold Emits an `OWNED_MODULES.json` Manifest

`auto-chain.ts` writes a sidecar file `.agentics/plans/scaffold/OWNED_MODULES.json`:

```json
{
  "version": "1.0",
  "owned": [
    { "path": "src/logger.ts", "exports": ["Logger", "createLogger", "setCorrelationId", "getCorrelationId"] },
    { "path": "src/config.ts", "exports": ["AppConfig", "config"] },
    { "path": "src/errors.ts", "exports": ["AppError", "ValidationError", "NotFoundError", "ERPError"] },
    { "path": "src/middleware.ts", "exports": ["correlationId", "requestLogger", "metricsHandler", "incrementCounter", "recordHistogram"] },
    { "path": "src/circuit-breaker.ts", "exports": ["CircuitBreaker"] },
    { "path": "src/simulation-lineage.ts", "exports": ["SimulationLineage", "loadSimulationLineage", "requireSimulationLineage"] }
  ]
}
```

The manifest is the single source of truth for what the generator must NOT re-implement.

### 4. Implementation Prompt Injection

`src/pipeline/phase2/phases/prompt-generator.ts` reads `OWNED_MODULES.json` and injects into every coding prompt:

```
🛑 SCAFFOLD-OWNED MODULES — DO NOT REIMPLEMENT:
The following modules already exist in the project at the listed paths.
You MUST import from them. You MUST NOT create files with overlapping exports.

  - src/logger.ts → Logger, createLogger, setCorrelationId, getCorrelationId
  - src/circuit-breaker.ts → CircuitBreaker
  - src/simulation-lineage.ts → loadSimulationLineage, requireSimulationLineage
  - ...

If your implementation needs one of these types, import it. Do not redefine it.
```

### 5. Post-Generation Validator Enforces the Rule

Add to ADR-PIPELINE-065's validator:

| ID | Rule | File Pattern | Check |
|---|---|---|---|
| PGV-012 | No generator-emitted file may redeclare an export listed in `OWNED_MODULES.json` | `src/**/*.ts` (excl. the scaffold-owned paths themselves) | For each owned export name, flag files matching `export\s+(class|function|const|interface)\s+<Name>` |

Error-severity. When PGV-012 fires, the fix is always "delete the duplicate and import from the owned path."

### 6. `auto-chain.ts` Cleanup Pass

After the generator finishes, `auto-chain.ts` runs a cleanup pass:
1. For each entry in `OWNED_MODULES.json`, if a generator-created file under a different path exports the same name, log `scaffold.duplicate.detected` and (if `AGENTICS_AUTO_DEDUPE=true`) delete the duplicate.
2. Emit a summary line: `Scaffold ownership: 6 owned modules, 0 duplicates detected`.

Auto-dedupe is opt-in because deleting files the agent just wrote is risky; the log alone is the default.

## Implementation

1. Extract `CircuitBreaker` into its own scaffold file in `src/pipeline/auto-chain.ts`.
2. Emit `OWNED_MODULES.json` alongside scaffold files.
3. Update `src/pipeline/phase2/phases/prompt-generator.ts` to read the manifest and inject the "do not reimplement" block.
4. Add PGV-012 to the post-generation validator (ADR-PIPELINE-065).
5. Add the cleanup pass at the end of `auto-chain.ts` scaffold emission.
6. Tests:
   - `tests/pipeline/scaffold/owned-modules.test.ts` — manifest shape
   - `tests/pipeline/validator/pgv-012.test.ts` — duplicate class detection
   - Integration test: run the pipeline against the OPERA query and assert no duplicate `CircuitBreaker`

## Acceptance Criteria

1. `.agentics/plans/scaffold/OWNED_MODULES.json` exists after every pipeline run.
2. `.agentics/plans/scaffold/src/circuit-breaker.ts` exists and `middleware.ts` re-exports from it.
3. A regenerated OPERA prototype contains exactly one `CircuitBreaker` class.
4. PGV-012 detects a synthetic duplicate `class CircuitBreaker` in a test fixture.
5. Implementation prompts contain the "SCAFFOLD-OWNED MODULES" block verbatim.
6. Running against the OPERA fixture produces `scaffold.duplicate.detected: 0`.

## Consequences

### Positive
- Eliminates a class of dead-code defects that would multiply as the scaffold grows
- Single source of truth for cross-cutting modules — bug fixes land once
- The manifest enables future tooling (upgrades, refactors, breaking-change detection)

### Negative
- Requires updating the prompt template every time a new scaffold module is added — mitigated by driving both from the manifest
- Auto-dedupe deletes files the agent wrote; opt-in until we trust the manifest
- Legacy generators that import their own `CircuitBreaker` need a one-time migration — ship a codemod alongside the first enforcement release
