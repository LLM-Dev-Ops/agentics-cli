# ADR-PIPELINE-077: ERP Schema Provenance Tag — Mark Unverified Schemas Explicitly

**Status:** Accepted
**Date:** 2026-04-12
**Priority:** HIGH — ERP readiness is flagged on every review
**Originating Review:** Ramco Aviation Catering Readiness Review (2026-04-12), ERP Readiness 7/10
**Prior Reviews:** OPERA (2026-04-11) flagged the same on Oracle Hospitality OPERA
**Builds on:** ADR-PIPELINE-050 (ERP Resilience), ADR-PIPELINE-058 (ERP Surface — Archibus Targeting)

## Context

Every review where the pipeline generates an ERP adapter notes the same issue:

> "The Ramco schema in erp/schema.ts is plausible but invented — it needs validation against the actual Ramco Aviation 'Flight Catering Order' document catalog with a Ramco SME before the first real call."
> — Ramco review 2026-04-12, ERP Readiness 7/10
>
> "Missing for real pilot: actual HTTP transport (only InMemoryOperaTransport exists), OAuth/token handling, and per-region OPERA endpoint routing."
> — OPERA review 2026-04-11, ERP Readiness 7/10

The generator produces Zod schemas that **look** plausible — field names mirror the target system's conventions, types are reasonable, and the data flow is correct. But no human has validated them against a real document catalog. A pilot team deploying this adapter in front of a live ERP would get silent schema-mismatch rejections, and the only way they'd know is by watching error logs.

The review's mitigation ("mark as 'unverified — pilot-only' in a top-of-file comment") is correct but manual. The pipeline should enforce the tag mechanically — not as a comment that an agent may or may not add, but as a typed metadata block that other parts of the pipeline can read and react to.

## Decision

### 1. Every Generated ERP Adapter/Schema Carries a Provenance Block

Every generated file under `src/erp/**` that touches external ERP schemas MUST export a `ERP_SCHEMA_PROVENANCE` constant with a typed shape:

```typescript
// src/erp/schema.ts (generated file)

import type { ErpSchemaProvenance } from './schema-provenance.js';

export const ERP_SCHEMA_PROVENANCE: ErpSchemaProvenance = {
  erp_system: 'Ramco Aviation',
  module: 'Flight Catering Order',
  source: 'invented',                     // 'invented' | 'catalog' | 'validated'
  catalog_version: null,                  // set when source = 'catalog' or 'validated'
  validated_at: null,                     // ISO date when source = 'validated'
  reviewer: null,                         // SME name + role when source = 'validated'
  notes: 'Generated from query + sector knowledge. NOT verified against a Ramco document catalog. Pilot deployment requires an SME review before the first live call.',
};
```

The block is **mandatory** and enforced by PGV-020. A generated ERP adapter without the block fails the post-generation validator.

### 2. Shared Type in Scaffold

A new scaffold file `src/erp/schema-provenance.ts` (owned by the scaffold per ADR-069) defines the type:

```typescript
// Auto-generated by Agentics pipeline (ADR-PIPELINE-077)
// Provenance tag for generated ERP schemas. MANDATORY on every file
// under src/erp/ that exports Zod schemas targeting an external ERP.

export type ErpProvenanceSource = 'invented' | 'catalog' | 'validated';

export interface ErpSchemaProvenance {
  /** Name of the target ERP system — e.g. 'Ramco Aviation', 'Oracle OPERA'. */
  readonly erp_system: string;
  /** The specific module the schema targets — 'Flight Catering Order'. */
  readonly module: string;
  /** Validation stage: invented (no review), catalog (field names match),
   *  validated (SME-reviewed against live docs). */
  readonly source: ErpProvenanceSource;
  /** Version identifier of the catalog source, when known. */
  readonly catalog_version: string | null;
  /** ISO timestamp of SME review when source='validated'. */
  readonly validated_at: string | null;
  /** Reviewer name + role when source='validated'. */
  readonly reviewer: { name: string; role: string } | null;
  /** Free-text notes visible in startup logs and generated README. */
  readonly notes: string;
}

/** Assert that an ERP adapter is allowed to run in the current environment. */
export function assertErpProvenanceOrFail(
  provenance: ErpSchemaProvenance,
  env: NodeJS.ProcessEnv = process.env,
): void {
  const strict = env['AGENTICS_ERP_STRICT'] === 'true';
  if (strict && provenance.source === 'invented') {
    throw new Error(
      `ECLI-ERP-077: ERP adapter for ${provenance.erp_system}/${provenance.module} has source='invented' ` +
      `and AGENTICS_ERP_STRICT=true. Pilot deployment requires an SME review — set source='validated' ` +
      `and provide reviewer + catalog_version before enabling strict mode.`,
    );
  }
}

/** Console-friendly banner for startup logs + demo output. */
export function formatProvenanceBanner(provenance: ErpSchemaProvenance): string {
  const icon = provenance.source === 'validated' ? '✅' :
               provenance.source === 'catalog'   ? '🟡' :
                                                    '⚠️ ';
  const lines: string[] = [
    `${icon} ERP SCHEMA PROVENANCE — ${provenance.erp_system} / ${provenance.module}`,
    `   source: ${provenance.source}`,
  ];
  if (provenance.catalog_version) lines.push(`   catalog: ${provenance.catalog_version}`);
  if (provenance.validated_at) lines.push(`   validated: ${provenance.validated_at}`);
  if (provenance.reviewer) lines.push(`   reviewer: ${provenance.reviewer.name} (${provenance.reviewer.role})`);
  if (provenance.source === 'invented') {
    lines.push(
      '   ',
      '   WARNING: This schema has not been validated against a real ERP document catalog.',
      '   Pilot deployment requires an SME review before the first live call.',
      '   Set AGENTICS_ERP_STRICT=true in production to block runs until source=\'validated\'.',
    );
  }
  return lines.join('\n');
}
```

Add to `OWNED_SCAFFOLD_MODULES`:

```typescript
{ path: 'src/erp/schema-provenance.ts',
  exports: ['ErpProvenanceSource', 'ErpSchemaProvenance', 'assertErpProvenanceOrFail', 'formatProvenanceBanner'] },
```

### 3. Adapter Startup Logs the Banner

Every generated ERP adapter imports `formatProvenanceBanner` and logs it at startup:

```typescript
// Somewhere in ErpAdapter constructor:
this.logger.warn('erp.provenance', {
  provenance: ERP_SCHEMA_PROVENANCE,
  banner: formatProvenanceBanner(ERP_SCHEMA_PROVENANCE),
});
assertErpProvenanceOrFail(ERP_SCHEMA_PROVENANCE);
```

The `assertErpProvenanceOrFail` call is a **runtime gate** — under `AGENTICS_ERP_STRICT=true` the process refuses to start when the schema is invented. Non-strict mode logs a warning and continues.

### 4. Demo Output Prints the Banner

The generated demo script's first output line is the provenance banner, so a pilot team running `npm run demo` sees at a glance whether they're looking at real or invented schemas:

```
> npm run demo

⚠️  ERP SCHEMA PROVENANCE — Ramco Aviation / Flight Catering Order
   source: invented

   WARNING: This schema has not been validated against a real ERP document catalog.
   Pilot deployment requires an SME review before the first live call.
   ...

CATER-WASTE COPILOT — PROTOTYPE DEMO
```

The demo scaffold template adds a `printProvenanceBanner()` call at the top.

### 5. Generated README Section

Every generated project's `README.md` MUST include a `## ERP Integration — Provenance` section auto-populated by the scaffold generator:

```markdown
## ERP Integration — Provenance

This project integrates with **Ramco Aviation / Flight Catering Order**.

| Field | Value |
|---|---|
| Source | **invented** |
| Catalog version | _not set_ |
| Validated at | _not set_ |
| Reviewer | _not set_ |

⚠️  **The generated Zod schemas have not been validated against a real Ramco
document catalog.** Before first live deployment:

1. Obtain the Ramco Aviation API reference or partner catalog
2. Diff the field names in `src/erp/schema.ts` against the catalog
3. Update `ERP_SCHEMA_PROVENANCE` in `src/erp/schema.ts`:
   - `source: 'validated'`
   - `catalog_version: 'v2024.1'` (or the version reviewed)
   - `validated_at: '2026-XX-XX'`
   - `reviewer: { name: 'Jane Doe', role: 'Ramco Integration Lead' }`
4. Set `AGENTICS_ERP_STRICT=true` in the pilot environment to enforce
   the validated state
```

### 6. PGV-020 — Every ERP Adapter File Has a Provenance Block

Add to the post-generation validator:

| ID | Rule | File Pattern | Check |
|---|---|---|---|
| PGV-020 | ERP adapter/schema files must export `ERP_SCHEMA_PROVENANCE` | `src/erp/**/*.ts` (excl. tests, scaffold-owned paths) | Match `export const ERP_SCHEMA_PROVENANCE\s*:\s*ErpSchemaProvenance` — error severity |

The rule fails any generated project that has ERP schemas without the block. The fix is mechanical and the validator prints a suggested snippet.

### 7. PGV-021 — No `source: 'validated'` Without Reviewer

Companion rule to prevent rubber-stamped validation:

| ID | Rule | File Pattern | Check |
|---|---|---|---|
| PGV-021 | `source: 'validated'` requires non-null `reviewer` and `catalog_version` | `src/erp/**/*.ts` | Parse `ERP_SCHEMA_PROVENANCE`; when `source === 'validated'` and either field is null, error |

Prevents a coding agent from setting `source: 'validated'` to quiet the strict-mode gate without actually recording the SME review.

### 8. Prompt Updates

`src/pipeline/phase2/phases/prompt-generator.ts` cross-cutting footer adds:

> ## ERP Schema Provenance (ADR-PIPELINE-077)
>
> When you generate ERP adapters (`src/erp/schema.ts`, `src/erp/<system>-adapter.ts`, etc.):
>
> 1. Import `ErpSchemaProvenance` from `src/erp/schema-provenance.ts`
> 2. Export a constant `ERP_SCHEMA_PROVENANCE` with `source: 'invented'` as the default
> 3. Set `notes` to a specific description of what you generated and why it needs review
> 4. In the adapter constructor, call `assertErpProvenanceOrFail(ERP_SCHEMA_PROVENANCE)`
>    so strict-mode deployments block on unreviewed schemas
> 5. In the demo script, print `formatProvenanceBanner(ERP_SCHEMA_PROVENANCE)` before
>    any business logic runs
>
> NEVER set `source: 'validated'` in generated code — that status is reserved for
> the pilot team after they've diffed the schema against the real ERP catalog.

## Implementation

1. New scaffold constant `ERP_SCHEMA_PROVENANCE_SCAFFOLD` in `src/pipeline/auto-chain.ts`; emitted to `src/erp/schema-provenance.ts`.
2. Add the new module to `OWNED_SCAFFOLD_MODULES`.
3. Update the `generate-adapter` prompt template in `src/pipeline/phase4/phases/http-server-generator.ts` (or wherever ERP adapters get prompted) to inject the provenance-block requirement.
4. Add `RULE_PGV_020` and `RULE_PGV_021` to `post-generation-validator.ts`. PGV-021 parses the `ERP_SCHEMA_PROVENANCE` literal with a lightweight AST-less scan (regex over the exported object).
5. Update README-generator template to include the `## ERP Integration — Provenance` section sourced from the block.
6. Update demo-script template to call `printProvenanceBanner()` at entry.
7. Tests:
   - `tests/unit/pipeline/scaffold/erp-provenance-077.test.ts` — compile the scaffolded helper, verify `assertErpProvenanceOrFail` throws under strict + invented, passes under non-strict or validated
   - PGV-020 positive + negative
   - PGV-021 positive + negative (missing reviewer under validated)

## Acceptance Criteria

1. Every generated project contains `src/erp/schema-provenance.ts` with the types and helpers.
2. Every generated ERP adapter file exports `ERP_SCHEMA_PROVENANCE` with `source: 'invented'` as default.
3. Running the generated demo prints the provenance banner before any business logic output.
4. Under `AGENTICS_ERP_STRICT=true`, the generated service refuses to start when `source='invented'` — exits with code 77 and `ECLI-ERP-077` in stderr.
5. PGV-020 fires against a synthetic adapter file missing the block.
6. PGV-021 fires against a fixture setting `source: 'validated'` with null reviewer.
7. Every generated README contains the `## ERP Integration — Provenance` table.

## Consequences

### Positive

- Pilot teams know immediately whether they're dealing with real or invented schemas — there is no way to miss the warning.
- Strict mode gives security/operations teams a kill switch for production deployments pending SME review.
- The reviewer field becomes an auditable record of who validated the schema and when — useful for change management when the ERP upgrades and the schema drifts.
- The banner appearing in demo output means the CLI evaluator sees it too, closing the documentation loop.

### Negative

- Every generated ERP adapter grows by ~20 lines (provenance block + import + constructor call). Acceptable.
- `AGENTICS_ERP_STRICT=true` will break existing pilots that haven't updated their provenance — rollout must be gradual. Default to non-strict for the first month; flip in a follow-up release.
- PGV-021's reviewer check is regex-based and can be bypassed with a fake name. That's fine — this is not a cryptographic guarantee, it's a forcing function.
