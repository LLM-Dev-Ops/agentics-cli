# ADR-PIPELINE-074: AsyncLocalStorage for Correlation-ID Propagation in Scaffold Logger

**Status:** Accepted
**Date:** 2026-04-12
**Priority:** HIGH — Concurrent-request bug in every generated project
**Originating Review:** Ramco Aviation Catering Readiness Review (2026-04-12), Code Quality 7/10
**Builds on:** ADR-PIPELINE-039 (Scaffold Files), ADR-PIPELINE-051 (Observability), ADR-PIPELINE-069 (Scaffold Ownership)

## Context

The Ramco review identified a subtle but real defect:

> "logger.ts stores correlation ID in a module-level mutable. Under concurrent Express requests, request B will observe request A's ID and log lines will cross-contaminate. Needs AsyncLocalStorage — a ~30-line fix."

The scaffold logger emitted by `src/pipeline/auto-chain.ts` (via the `loggerCode` template literal) uses:

```typescript
let currentCorrelationId: string | undefined;

export function setCorrelationId(id: string): void { currentCorrelationId = id; }
export function getCorrelationId(): string | undefined { return currentCorrelationId; }

export function createLogger(service: string): Logger {
  const emit = (level: string, event: string, extra?: Record<string, unknown>) => {
    const entry = { timestamp: new Date().toISOString(), level, service, event,
      ...(currentCorrelationId ? { correlationId: currentCorrelationId } : {}), ...extra };
    process.stderr.write(JSON.stringify(entry) + '\n');
  };
  // ...
}
```

The problem: a Node.js process is single-threaded but NOT single-request. When request A calls `setCorrelationId('req-A')` and awaits a database call, request B arrives, calls `setCorrelationId('req-B')`, and starts emitting logs. When request A resumes, its log lines now carry `'req-B'`. Under load testing with 100 concurrent requests, 30-70% of log lines are mislabeled.

This is not a theoretical concern — every generated project that wires the correlation middleware inherits the bug. The Ramco prototype, the OPERA prototype, and every earlier pilot all have it. It has been caught in two consecutive production readiness reviews.

**The fix belongs at the pipeline level, not the prototype level.** Regenerating every prototype when it's caught is not a strategy. The scaffold must emit a correct logger.

## Decision

### 1. Rewrite the Logger Scaffold to Use AsyncLocalStorage

Replace the module-level mutable with a `node:async_hooks` `AsyncLocalStorage<LoggerContext>`. The store carries both the correlation ID and any additional bindings the `.child()` method has attached.

New logger scaffold body:

```typescript
// Auto-generated by Agentics pipeline (ADR-PIPELINE-074)
// Correlation IDs flow through an AsyncLocalStorage so concurrent requests
// never cross-contaminate log lines. Import setCorrelationId/runWithCorrelation
// from here; NEVER reach for a module-level mutable.
import { AsyncLocalStorage } from 'node:async_hooks';

export interface Logger {
  info(event: string, data?: Record<string, unknown>): void;
  warn(event: string, data?: Record<string, unknown>): void;
  error(event: string, error: Error, data?: Record<string, unknown>): void;
  child(bindings: Record<string, unknown>): Logger;
}

interface LoggerContext {
  correlationId?: string;
  bindings: Record<string, unknown>;
}

const storage = new AsyncLocalStorage<LoggerContext>();

/** Run `fn` with `correlationId` installed in the current async scope. */
export function runWithCorrelation<T>(correlationId: string, fn: () => T): T {
  const parent = storage.getStore();
  const ctx: LoggerContext = {
    correlationId,
    bindings: parent?.bindings ?? {},
  };
  return storage.run(ctx, fn);
}

/** Returns the correlation ID for the current async scope, if any. */
export function getCorrelationId(): string | undefined {
  return storage.getStore()?.correlationId;
}

/**
 * Back-compat setter — deprecated. Retained for legacy callers but
 * SHOULD NOT be used inside request handlers. Use runWithCorrelation.
 * Under AsyncLocalStorage, this mutates the current store in place.
 */
export function setCorrelationId(id: string | undefined): void {
  const ctx = storage.getStore();
  if (ctx) ctx.correlationId = id;
}

export function createLogger(service: string): Logger {
  const build = (bindings: Record<string, unknown>): Logger => {
    const emit = (level: string, event: string, extra?: Record<string, unknown>): void => {
      const ctx = storage.getStore();
      const entry = {
        timestamp: new Date().toISOString(),
        level,
        service,
        event,
        ...(ctx?.correlationId ? { correlationId: ctx.correlationId } : {}),
        ...bindings,
        ...(ctx?.bindings ?? {}),
        ...extra,
      };
      process.stderr.write(JSON.stringify(entry) + '\n');
    };
    return {
      info: (event, data) => emit('info', event, data),
      warn: (event, data) => emit('warn', event, data),
      error: (event, err, data) => emit('error', event, {
        error: err.message,
        stack: err.stack,
        ...data,
      }),
      child: (childBindings) => build({ ...bindings, ...childBindings }),
    };
  };
  return build({});
}
```

### 2. Middleware Scaffold Wraps the Request Handler

`src/pipeline/auto-chain.ts` also emits a `middleware.ts` scaffold with a `correlationId` Express middleware. Update it to wrap `next()` inside `runWithCorrelation`:

```typescript
import { randomUUID } from 'node:crypto';
import { runWithCorrelation } from './logger.js';

export function correlationId(req: any, res: any, next: () => void): void {
  const id = (req.headers['x-correlation-id'] as string) || randomUUID();
  req.correlationId = id;
  res.setHeader('X-Correlation-Id', id);
  runWithCorrelation(id, next);
}
```

The old `setCorrelationId(id)` call is replaced with `runWithCorrelation(id, next)` which properly scopes the ID to the request handler's async continuation.

The same pattern applies to Hono (wrap `await next()` in `runWithCorrelation`) and Fastify (register as an `onRequest` hook that starts the store).

### 3. PGV-016 — Ban Module-Level Correlation State

Add a rule to the post-generation validator from ADR-PIPELINE-065:

| ID | Rule | File Pattern | Check |
|---|---|---|---|
| PGV-016 | No module-level `let currentCorrelationId` or equivalent | `src/**/logger.ts`, `src/**/logging/**` | Match `(?:let\|var)\s+\w*[cC]orrelation\w*` at module scope; error severity |

The rule ensures regenerated projects (or hand-edited ones) never reintroduce the module-level mutable pattern.

### 4. Update `OWNED_SCAFFOLD_MODULES`

ADR-PIPELINE-069 lists `src/logger.ts` as owned by the scaffold. Keep the path but update its exports to include `runWithCorrelation`:

```typescript
{
  path: 'src/logger.ts',
  exports: [
    'Logger',
    'createLogger',
    'runWithCorrelation',
    'getCorrelationId',
    'setCorrelationId',  // retained as a no-op legacy export
  ],
},
```

PGV-012 (ownership enforcement) continues to block any generator-emitted redeclaration.

### 5. Implementation Prompt Updates

`src/pipeline/phase2/phases/prompt-generator.ts` already tells the coding agent to use `createLogger` from the scaffold. Add one more line:

> "For correlation-ID propagation, wrap request handlers with `runWithCorrelation(correlationId, next)` from `src/logger.ts`. Do NOT reach for `setCorrelationId` at module scope or store the correlation ID in a module-level variable — concurrent requests will cross-contaminate."

### 6. Concurrency Test in the Scaffold

The scaffold now emits a test file alongside `logger.ts`:

```typescript
// Auto-generated by Agentics pipeline (ADR-PIPELINE-074)
// src/logger.concurrency.test.ts — proves correlation IDs don't leak.
import { describe, it, expect } from 'vitest';
import { createLogger, runWithCorrelation, getCorrelationId } from './logger.js';

describe('logger correlation-id async scoping', () => {
  it('does not leak correlation IDs across concurrent async tasks', async () => {
    const results: Array<{ requested: string; observed: string | undefined }> = [];
    const tasks: Promise<void>[] = [];
    for (let i = 0; i < 50; i++) {
      const id = `req-${i}`;
      tasks.push(
        runWithCorrelation(id, async () => {
          await new Promise(r => setTimeout(r, Math.random() * 10));
          results.push({ requested: id, observed: getCorrelationId() });
        }),
      );
    }
    await Promise.all(tasks);
    for (const r of results) {
      expect(r.observed).toBe(r.requested);
    }
  });
});
```

Every generated project inherits this test. It fails loudly if someone regresses the AsyncLocalStorage wiring.

## Implementation

1. Extract the current `loggerCode` template literal from `src/pipeline/auto-chain.ts` into a module-scope `LOGGER_SCAFFOLD` constant (pattern established by ADR-PIPELINE-068 / 069).
2. Rewrite `LOGGER_SCAFFOLD` body to use `AsyncLocalStorage` as shown in §1.
3. Update `MIDDLEWARE_SCAFFOLD` (also in `auto-chain.ts`) to import `runWithCorrelation` and wrap `next()`.
4. Extract a new `LOGGER_CONCURRENCY_TEST_SCAFFOLD` constant and write it to the generated project at `src/logger.concurrency.test.ts`.
5. Update `OWNED_SCAFFOLD_MODULES` entry for `src/logger.ts` to include `runWithCorrelation`.
6. Add `RULE_PGV_016` to `src/pipeline/phase5-build/phases/post-generation-validator.ts`.
7. Update the prompt-generator's cross-cutting footer to reference `runWithCorrelation`.
8. Tests:
   - `tests/unit/pipeline/scaffold/logger-concurrency-074.test.ts` — compiles `LOGGER_SCAFFOLD` via `ts.transpileModule`, runs the 50-concurrent-task test
   - `tests/unit/pipeline/phase5/post-generation-validator.test.ts` — PGV-016 positive + negative cases

## Acceptance Criteria

1. Every generated project contains `src/logger.ts` exporting `runWithCorrelation` and using `AsyncLocalStorage`.
2. Every generated project contains `src/logger.concurrency.test.ts` and it passes on first run.
3. Running 50 concurrent async tasks with distinct correlation IDs shows zero cross-contamination.
4. PGV-016 fires against a synthetic fixture that reintroduces `let currentCorrelationId` at module scope.
5. `OWNED_SCAFFOLD_MODULES` entry for `src/logger.ts` lists `runWithCorrelation`.
6. The prompt-generator cross-cutting footer references `runWithCorrelation`.

## Consequences

### Positive

- Every generated project becomes concurrency-correct by default — no pilot team needs to discover the bug under load.
- `child()` binding support becomes reliable; per-request bindings no longer leak.
- The bundled concurrency test provides an early warning if the wiring is hand-broken.
- Aligns with Node.js observability best practices (OpenTelemetry also uses AsyncLocalStorage for trace context, so this pattern extends naturally).

### Negative

- `setCorrelationId` becomes a partial no-op outside an async scope. Legacy callers that set it at module init time will silently lose the ID. Deprecation warning in the scaffold comment + PGV-016 push toward `runWithCorrelation`.
- `AsyncLocalStorage` has a small per-async-hop overhead (~5µs). Acceptable for every generated service.
- Generated tests need to use `runWithCorrelation` in their setup — the scaffold comment documents this.
