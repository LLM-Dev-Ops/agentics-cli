# ADR-068: Domain Route RBAC Enforcement and Telemetry Parity

## Status: IMPLEMENTED

## Date: 2026-03-31

## Context

The Agentics pipeline generates domain-specific route modules tailored to whatever enterprise context the user describes — climate risk, supply chain logistics, financial planning, compliance workflows, etc. These domain routes are the primary API surface for the generated system.

Production readiness audit (2026-03-31) of a climate risk pipeline run found that the generated domain routes (`src/server/climate-routes.ts`) bypass the IAM/RBAC middleware stack that the core scaffold routes (`routes.ts`) enforce. **This is a structural issue in the pipeline's code generation, not a climate-specific bug.** Any domain the pipeline generates will have the same gap unless the generation step is fixed.

The two gaps:

1. **RBAC bypass (CRITICAL)**: Domain routes are mounted as a separate Hono app and never pass through `requireRole()` middleware. The core `routes.ts` correctly enforces role checks (viewer, writer, approver, erp_writer, admin) per ADR-049, but domain routes generated by Phase 4/LLM codegen are mounted outside the middleware chain. This means any authenticated user — regardless of role — can access all domain endpoints, including simulation, ERP writeback, and approval workflows.

2. **Telemetry gap (HIGH)**: Domain route handlers have no `telemetry.withSpan()` wrapping, no correlation ID propagation, and no structured error logging. The core `routes.ts` wraps every handler in telemetry spans via `deps.telemetry`. Domain route failures are invisible in monitoring.

### Why This Happens

The pipeline generates two route files independently:
- `routes.ts` — scaffolded with full middleware integration (JWT, RBAC, telemetry, audit, correlation IDs)
- `{domain}-routes.ts` — generated from domain model and simulation context, but without the middleware wiring

The codegen prompt for domain routes doesn't enforce middleware parity with the core routes. This is the root cause.

### Impact (applies to ANY domain the pipeline generates)

- An attacker with any valid JWT (even a `viewer` role) can trigger ERP writeback via domain routes
- Simulation runs have no observability — failures are silent
- Compliance auditors cannot verify who accessed domain-specific data or when

## Decision

### 1. Pipeline codegen MUST enforce middleware parity for all generated route modules

The LLM codegen prompt (ADR-067) for domain route generation must include an explicit constraint:

```
CONSTRAINT: All generated route modules MUST be mounted through the same middleware
chain as routes.ts. Every route handler MUST:
- Inherit correlationId, requestLogger, and jwtVerify middleware from the parent app
- Apply requireRole() with appropriate roles per endpoint
- Wrap handler logic in deps.telemetry.withSpan()
- Call deps.audit.log() for state-changing operations
```

This makes middleware parity a **generation-time guarantee**, not a manual post-generation fix.

### 2. Role classification by operation type (domain-agnostic)

Instead of mapping roles to domain-specific endpoint names, classify by operation semantics:

| Operation Type | Required Role(s) | Examples (any domain) |
|---|---|---|
| **Read reference data** | viewer, writer, admin | GET suppliers, GET scenarios, GET entities |
| **Read assessments/analysis** | viewer, writer, admin | GET impact analysis, GET coverage gaps, GET risk scores |
| **Run simulations** | writer, admin | POST simulate, POST scenario-compare, POST what-if |
| **Initiate ERP writeback** | erp_writer, admin | POST erp/update, POST erp/sync |
| **Approve/reject writeback** | approver, admin | POST erp/approve/:id, POST erp/reject/:id |
| **Admin operations** | admin | DELETE, bulk operations, config changes |

The codegen prompt should classify each generated endpoint into one of these operation types and apply the corresponding role check.

### 3. Telemetry wrapping pattern (domain-agnostic)

Every generated handler must follow this pattern:

```typescript
app.post('/simulate', requireRole('writer', 'admin'), async (c) => {
  return deps.telemetry.withSpan(`${domainPrefix}.simulate`, async (span) => {
    const correlationId = c.get('correlationId');
    span.setAttribute('correlationId', correlationId);
    try {
      // ... domain-specific handler logic
      return c.json(result);
    } catch (error) {
      span.setAttribute('error', true);
      span.setAttribute('error.message', error.message);
      deps.logger.error({ correlationId, error: error.message }, `${domainPrefix}.simulate failed`);
      return c.json({ error: 'Operation failed', correlationId }, 500);
    }
  });
});
```

The `domainPrefix` (e.g., `climate`, `logistics`, `compliance`) is derived from the pipeline's domain context and used consistently across span names, log entries, and metric labels.

### 4. Audit logging for all state-changing domain operations

All domain route handlers that modify state must call `deps.audit.log()` with:
- `action`: Operation name (e.g., `SIMULATE_SCENARIOS`, `REQUEST_ERP_WRITEBACK`)
- `actor`: From JWT claims
- `resource`: Entity ID or endpoint path
- `correlationId`: From middleware
- `inputHash`: For simulation operations (lineage traceability)

### 5. Post-generation validation check

Add a pipeline validation step that scans generated domain routes for middleware compliance:

```typescript
// Pipeline Phase 5 or post-generation hook
function validateRouteMiddlewareParity(generatedRouteFile: string): ValidationResult {
  const source = readFileSync(generatedRouteFile, 'utf-8');
  const issues: string[] = [];

  // Check: every route handler uses requireRole()
  if (!source.includes('requireRole')) {
    issues.push('No RBAC middleware detected — domain routes bypass role checks');
  }

  // Check: telemetry spans present
  if (!source.includes('withSpan')) {
    issues.push('No telemetry spans — domain route operations will be invisible');
  }

  // Check: audit logging present for POST/PUT/DELETE
  if (source.match(/\.(post|put|delete)\(/g) && !source.includes('audit.log')) {
    issues.push('State-changing endpoints without audit logging');
  }

  return { valid: issues.length === 0, issues };
}
```

This catches the gap at generation time rather than in production audit.

## Consequences

### Positive
- Every domain the pipeline generates — climate, logistics, finance, compliance, whatever — gets RBAC, telemetry, and audit logging automatically
- The fix is structural (in the codegen prompt and validation) rather than per-domain
- Role classification by operation type works across any business domain
- Post-generation validation prevents regression

### Negative
- Existing generated codebases need a one-time manual fix to add middleware wiring
- LLM codegen prompts become slightly longer with the middleware constraint
- Integration tests for domain routes will need JWT fixtures (one-time test infrastructure investment)

## Implementation Priority

**CRITICAL — Day 1 of pilot preparation.** Two tracks:

1. **Immediate (this pipeline run):** Wire the existing domain routes through the middleware chain manually. ~3-4 hours.
2. **Structural (pipeline fix):** Update the LLM codegen prompt and add the post-generation validation check. ~2-3 hours. This prevents the issue from recurring on future pipeline runs regardless of domain.
